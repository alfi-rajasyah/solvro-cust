# Backend conventions (Express + Prisma + PostgreSQL 15)

Sub-200ms API response is a non-functional requirement — design queries and indexes accordingly.

- **Entrypoint**: `src/index.ts` boots; the app is built in `src/app.ts` (split for testability).
- **No `/api` prefix**: routers mount bare (`/auth`, `/projects`, …). The frontend's `/api` base still works because the vite dev proxy and prod nginx both strip `/api` before forwarding.
- **Env**: `src/env.ts` parses `process.env` via Zod and exits on failure. Import from `./env.js` — never read `process.env` directly.
- **Prisma**: single shared client `src/prisma.ts` — never `new PrismaClient()` in a route (standalone scripts under `scripts/` and `prisma/seed.ts` are the only exception). Tables/columns are `@map`ped snake_case; the TS surface is camelCase.
- **Auth**: `src/http/auth.ts`. `router.use(requireAuth)` once at the top of every authed router; authorize actions with `requirePermission("project:write" | "task:write" | …)`; `requireAdmin` gates `/admin`. The JWT carries only `{ sub, ver, auth_time }` (`auth_time` = original sign-in, passed through unchanged by `POST /auth/refresh`, which never extends a session past `SESSION_MAX_AGE_SECONDS` after it — a refusal is 409 `session_max_age`, never 401); `requireAuth` loads the user and its role on every request (two primary-key queries) and builds `req.user` (`{ sub, role, permissions }`) from the database — role and permission changes apply on the next request — short-circuiting if `req.user` is already set (several routers share a mount). Failures are 401 `unauthenticated` (unknown account, missing/invalid token), `account_disabled`, or `token_revoked` (stale `ver`, or a legacy token without one); `User.tokenVersion` is bumped on password change, admin password reset and deactivation. `hasPermission(user, "*")` is the wildcard short-circuit. Authorization is permission-based, never role-name-based — admins can create custom roles with arbitrary permission arrays. **A route answers 401 only for a session failure** — the frontend signs the user out on any 401 from an authenticated request, so a refused action is 403 (a 403 `forbidden` makes the client re-read `/auth/me`), 400 or 409, never 401. The sign-in routes (`/auth/login`, `/auth/google`) throttle *failures* per email and per client address (`http/loginThrottle.ts`, 429 `rate_limited` + `Retry-After`; successes never count) and answer every rejected password sign-in with the same `invalid_credentials` — never a code that reveals whether an email exists or which provider it uses — and always run one `bcrypt.compare` (against a dummy hash when there is no stored one) so the answer takes the same time. The per-email lockout this creates is an accepted risk (`docs/ISSUES.md`). Project data routers (`/projects`, `/tasks`, `/epics`, `/overview`) gate every read on `project:read` at router level.
- **Visibility**: `src/lib/visibility.ts`. `projectVisibilityFilter(user)`: `project:view-all` (or `*`) sees everything; everyone else matches the project's TAM (`tamId`), OR ownership of the project's customer (`customer.tamId`), OR membership (`ProjectMember`) — each arm grants the same full access as being the project's own TAM, not just a read (docs/archive/plans/collaboration-and-sharing.md). `customerVisibilityFilter(user)`: view-all sees every customer; everyone else sees a customer they own (`tamId`), an unowned customer (`tamId` null), or a customer with at least one visible project (so it inherits the member arm). `canUserSeeProject(user, facts)` in `lib/visibility.ts` is the in-memory twin of `projectVisibilityFilter` (used for batch recipient checks in `lib/notifications.ts`): any new visibility arm must be added to BOTH and to the parity test in `test/notifications.test.ts`. Both results' only top-level key is `OR` — AND-compose with any sibling `OR`, never object-spread. **Ownership changes are owner-only**: changing a project's TAM or customer, deleting a project, changing a customer's owner, or deleting a customer must not be allowed by membership alone — use `ensureProjectOwnerAccess`/`ensureCustomerOwnerAccess` (visibility 404 first, then 403 `owner_only`), which re-check with `{ viaMembership: false }` (drops the member arm; pass it to any new membership-excluding check). The exception is changing a customer's owner (`PATCH /customers/:id`), which uses an inline rule instead: the current owner or a `project:view-all` holder; on an unowned customer only a caller who is the TAM of every project under it (or it has none) — owning a customer grants every project under it, so being TAM of one project is not enough. `DELETE /customers/:id` still uses `ensureCustomerOwnerAccess`. Daily Review scope (`lib/dailyReviewScope.ts`) counts member projects as the caller's own. Id-keyed routes use `ensureProjectVisible`/`ensureTaskVisible`/`ensureCustomerVisible` (404 on purpose, not 403 — don't reveal that a hidden resource exists); a `customerId` taken as a body field (a project) uses `isCustomerVisible` instead and answers 400 `customer_not_found`. Reuse these — never re-derive scoping ad hoc.
- **Validation**: `validate("body" | "params" | "query", schema)` from `src/http/validate.ts`; Zod schemas at the top of the route file; `z.coerce.*` for query/params.
- **Errors**: throw `new HttpError(status, code, message)` from `src/http/errors.ts`; the global handler renders `{ error, code, details }`.
- **Logging**: shared pino logger from `src/logger.ts`; honor `LOG_LEVEL`.
- **Public (unauthenticated) surface**: lives only in `src/routes/publicShare.ts`, mounted in `app.ts` outside every authed router (`requireAuth` never runs there). Any new public route must be rate-limited via `src/http/rateLimit.ts`, answer every failure (unknown, expired, revoked, malformed) with the same uniform 404, set `Cache-Control: no-store` and `X-Robots-Tag: noindex`, and `select` only allow-listed columns — never return a whole row or an unfiltered relation. **Exceptions, and only these**: the signed webhooks in `src/routes/webhook.ts` (the iTop shared-secret header, the Outline HMAC signature — both mounted before `express.json()`, rate-limited, refused without a valid signature/secret) and the Outline OAuth callback `GET /outline/oauth/callback` in `src/routes/outline.ts`. The callback takes the user's identity only from its signed, single-use `state` row (never a cookie or bearer), is rate-limited, sends `no-store` / `noindex` / `Referrer-Policy: no-referrer`, and answers every outcome with a redirect to `${APP_URL}/settings` carrying a fixed reason code, never Outline's own text — the one exception is `APP_URL` unset, where there is nowhere to redirect and it answers a plain 404. A new unauthenticated route outside this list needs the full public-surface rules above.
- **Request logging**: goes through `src/http/requestLogger.ts`, which redacts guest-link tokens and the Outline OAuth callback's `code`/`state`, and masks the `Authorization`, `X-Solvro-Webhook-Secret`, `Outline-Signature`, `Cookie` and `Set-Cookie` headers (request and response). Never log a raw URL, `Referer`, or header object that may carry a secret; new secret-bearing paths must be added to its redaction.
- **Outline calls**: every call to Outline's API goes through `src/lib/outline/client.ts#outlineCall(userId, method, body)` with that user's own OAuth token (the Outline guardrail in the root `CLAUDE.md` — no application/admin token, no Outline API request from anywhere else; `rawOutlineCall` exists only for the OAuth callback's `auth.info` check on a token that is not stored yet, and the OAuth token endpoints live in `lib/outline/oauth.ts`). Outline response bodies can hold page text, so they are never logged or stored.
- **Migrations**: always `prisma migrate dev --name <slug>` — never edit committed SQL. The unique index on `lower(username)` exists only in migration `20261026090000_user_identity_case` (Prisma cannot express a functional index in `schema.prisma`, and does not report it as drift) — never drop it, and keep usernames compared case-insensitively. The trigram GIN indexes (`type: Gin`, `ops: raw("gin_trgm_ops")`) are declared in `schema.prisma`, so they are not drift.

## Traps

- `prisma migrate dev` is interactive and hangs without a TTY: `docker compose exec -it backend npx prisma migrate dev --name <slug>`. Non-interactive fallback: `prisma migrate diff --script` into a hand-created `prisma/migrations/<timestamp>_<slug>/migration.sql`, then `migrate deploy` + `prisma generate`.
- Plain `docker compose exec backend npm test` inherits the container's dev `DATABASE_URL`. `test/globalSetup.ts` hard-refuses to run against it — it throws before migrating or touching any data unless the database name ends in `_test` — so this fails loudly instead of polluting the dev DB. Isolate:
  `TEST_URL=$(docker compose exec backend printenv DATABASE_URL | tr -d '\r\n' | sed 's|/solvro?|/solvro_test?|') && docker compose exec -e DATABASE_URL="$TEST_URL" backend npm test` (globalSetup auto-migrates `solvro_test`, then truncates every table so each run starts from a clean database — no manual drop/recreate needed).
- **Never point `--shadow-database-url` at the dev database** (trap confirmed 2026-09-24: it wiped every row in `solvro`, including the admin user, and the migration history had to be re-baselined). Prisma resets the shadow database. For the non-interactive `migrate diff` fallback create a throwaway database first (`docker compose exec -T postgres createdb -U solvro solvro_shadow`) and pass that URL, then drop it.
- After `prisma migrate dev` (or `migrate deploy`), the long-running `backend` container's already-loaded Prisma Client is stale until `docker compose restart backend` — a route that reads/writes a column the migration renamed or dropped 500s with "column … does not exist" until the container restarts and reloads the generated client.
