# E2E conventions (Playwright)

- Two projects in `playwright.config.ts`: `desktop` (Desktop Chrome, 1440×900) and `mobile` (iPhone 13 viewport forced onto Chromium — CDP is required for touch-drag). `npm test` runs both; `npm run test:desktop` / `npm run test:mobile` split.
- `BASE_URL` defaults to `http://localhost:8080` — the built CI stack from `ci/docker-compose.ci.yml`. Against the dev server use `BASE_URL=http://localhost:5173`, where `pwa.spec.ts` skips itself (port 5173): vite-plugin-pwa serves the manifest/service-worker only in build/preview mode, so that spec only runs against :8080.
- Use the shared fixtures in `fixtures/` (`seed.ts`, `test.ts` — seeded project + admin credentials) instead of hand-seeding inside specs.
- Specs that change the workspace-wide status list or WIP limits must restore it, and the tasks they moved, in `afterAll` — they rely on `workers: 1` (CI shards still get fresh DBs).
- CI runs this suite in `.github/workflows/ci.yml`: boots the CI stack, waits on `:3300/health`, creates the admin via `create-admin.ts`, uploads traces on failure. It splits each project into 4 shards (`--shard=N/4`), each on its own fresh stack and database: PRs into `develop` run the desktop shards, pushes to `main` run desktop and mobile. Playwright shards by spec file, so a spec file must never depend on data another spec file created — the two may land on different stacks.
- **Every row a spec creates carries an e2e marker**, so `backend/scripts/dev/cleanup-e2e-data.ts` can remove it from the dev database after a local run: a customer's description starts with `e2e` and its name ends in the fixture stamp; a project is linked to such a customer or its name ends in the fixture stamp (`<Name> ${stamp}`, the stamp built as in `fixtures/seed.ts`); a user's email ends in `@solvro.test` (the sign-in account, `ADMIN_EMAIL`, is kept). Never attach a test project to an existing demo customer (such as `customers[0]`) without the stamp, and never create a user outside `@solvro.test`. A spec that cleans up after itself still follows this, because a failed run skips its teardown.
- **Restart the dev backend before running specs against `:5173` after adding a route.** The dev backend does not always serve a newly added route (`tsx watch` can miss the edit); run `docker compose restart backend` first, or the spec fails on a 404 that is not a test bug.
