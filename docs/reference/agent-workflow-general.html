A phase is a branch is a PR

Tasks are commits. Independent tasks run concurrently. A bash script certifies each wave the moment it integrates, and judgment is spent once, on the combined diff, right before you read the PR.

opus judgment hand-off dashed: return path, or a step that runs only when a trigger fires

Cheap generation, expensive judgment

Specialists divide by pipeline stage, not by discipline. Sonnet is the floor for every subagent and haiku is never used. The orchestrator is whatever model you started the session with.

Orchestrator

main session

The interactive session itself. It has no agent file because it is you and Claude in the terminal. It derives the task dependency graph, routes work, integrates waves, appends changelog entries serially, and does final acceptance against each task's criteria.

Never: commits or opens a PR on its own. It stages the work and drafts the message, then stops.

Implementor

sonnet-5

Executes exactly one scoped task per dispatch: code and tests in the same change set, verified with scoped checks only.

  • Re-reads the contract files every dispatch, never from memory
  • Runs its own area typecheck and the tests it touched, not the full gate script
  • Reports that output verbatim, including failures it could not fix
  • Reports its changelog text when it is part of a wave
Never: marks its own work verified, expands scope, or runs a git write command.

Reviewer

opus-5

One merged reviewer for code and design. It reads the contract files at review time rather than carrying an inline copy, because inline copies are what rot.

  • Grep and Bash exist so findings are evidence, not impressions
  • A claim about a value is checked in the source file, not the doc
  • Output is blocker, should-fix, nit, each with file:line
Never: has Write or Edit. Reviewers report, they do not fix.

gates.sh

zero agents

A bash script replaced the QA agent entirely. It costs no tokens and finishes in seconds. The orchestrator owns it and runs it serially at each wave integration, after interactive fixes, and at phase close. Two-layer verification survives: the layers are now script plus orchestrator acceptance, and an implementor still cannot certify itself.

Docs keeper

sonnet-5

Runs at phase end only when a deterministic trigger fires, so it is usually skipped. Its default action on a CLAUDE.md file is deletion, not addition: those files carry rules and traps, never current state.

Broken is known in seconds. Wrong can wait for review.

Every guardrail that must not depend on model attention became a grep. The script prints one line per check and exits non-zero if any of them fail, so the next wave never builds on broken code.

It is deliberately single-writer. Concurrent runs from a parallel wave fight over the same containers, ports, and test database, and cross-contaminate each other's results. A lock directory refuses a second run, and only the orchestrator starts one.

Compile and test conditional on the diff

api-typecheckapi-unitweb-typecheckweb-unitweb-unit-tze2e-smoke

Point the test gate at an isolated database, never your development one, or a parallel wave will corrupt the data you are looking at. Then run at least one suite a second time under a hostile condition: a different timezone, a non-English locale, a shifted clock. A suite that only ever runs in one environment is blind to every bug that lives in another.

Standing guardrails always, every task

changelog-presenceguardrail-route-existsguardrail-banned-depguardrail-pii-redactedguardrail-local-only-untrackedguardrail-vendor-patches

Each is one project invariant reduced to a grep. Write one for every rule you have caught yourself repeating in a prompt: a dependency that must never come back, a route that must never be deleted, a field that must never reach an export, a vendored file whose local edits must stay countable.

Boundary tripwire and lock

spine-reviewgates-lock

The spine check matches the diff against your spine list and refuses to pass until a review has actually been recorded for that task. The lock is a plain mkdir on a directory in the temp dir, released by an exit trap; a stale one is cleared with rmdir.

The spine is where one mistake breaks several surfaces

Every codebase has a small set of files that many screens quietly sit on. Break one and three things fail at once. A change confined to a single screen can wait for the phase review. A change to the spine gets expensive eyes the moment it lands.

The membership test is one sentence: if a single mistake in this file can break more than one surface, it belongs on the list. Keep the list short enough that touching it stays rare, or the instant review stops being instant.

Ordering and sequencing

Rank or position logic shared by a list, a board, and a timeline. Reorder arithmetic is easy to get subtly wrong and impossible to see from inside one view.

  • lib/ordering.ts
  • routes/items.ts

Serialization contracts

Dates, times, money, IDs. Anywhere a writer and a reader must agree on a format. These fail silently, and often only in some environments.

  • lib/dates.ts
  • components/DateField.tsx

Fetch and mutation layer

The hook or client every screen calls, together with its optimistic updates and its rollback path. A missing rollback shows up as data that silently reverts.

  • lib/queries.ts

Adapters to a view engine

The translation between your data model and whatever board, chart, or grid renders it. Rename one field here and the render breaks while the type check stays green.

  • components/board/adapter.ts
  • components/chart/mapper.ts

Vendored or forked code

Anything copied in from upstream. Re-pulling discards your local edits without a word unless something counts them, so mark every sanctioned edit and assert the count in a gate.

  • components/vendor/

Auth, schema, and infra

Permission checks, migrations, container and environment config. The blast radius is the whole application rather than one screen.

  • lib/permissions.ts
  • prisma/schema.prisma + migrations
  • compose.yml, .env, nginx.conf

Enforcement is mechanical, not model judgment. The script matches git diff --name-only against your list and fails the task unless --performed-review=opus is passed after a real review. Discretion routes the work; grep guards the boundary.

Every rule lives in one place and arrives four ways

Duplication is what rotted the first setup, so no product guardrail is ever copied into an agent file. Delivery is redundant instead: the same rule reaches an agent through automatic context, its own role file, the dispatch brief, and finally a script that does not care whether the model was paying attention.

Auto-loaded contract Subagents receive project CLAUDE.md automatically, so product rules live only there. Guardrails are user-owned and no agent may edit that block. CLAUDE.md + area files
Role guardrails Agent files carry only what the role may and may not do. Product facts embedded here proved able to drift, so a docs duty now syncs paths and commands that appear in them. .claude/agents/*.md
Dispatch brief The orchestrator passes the task verbatim with its paths and acceptance criteria, and flags which guardrails are hot for this specific change. A flagged rule beats a buried rule. per task, at spawn time
Mechanical enforcement Anything that must never depend on attention becomes a standing check. If a model forgets, the script does not. .claude/scripts/gates.sh

Constrain how the session talks back to you

The pipeline decides what the agents do. This decides what reaching you costs. A model that answers a yes-or-no question in four paragraphs is not being thorough, it is moving the reading work onto you. Write the rules down once and deliver them at session start.

Two constraints make or break this. Scope the rules to conversation only: they must never reach code, comments, commit messages, or any file you write. And do not put them in a CLAUDE.md. Every CLAUDE.md in the hierarchy reaches subagents, where "answer first" would strip the file:line evidence out of a reviewer's findings. A subagent's output is data for the orchestrator, not chat for a human, and it never gets a follow-up turn to supply the detail you cut.

A SessionStart hook fires for the main session alone, which is exactly the scope you want. Keep the rules in a file you can edit without touching the hook.

.claude/reply-style.md         the rules, edit here
.claude/hooks/reply-style.js   prints them as additionalContext
.claude/settings.local.json    registers the SessionStart hook

Verify the scope yourself rather than trusting a diagram: start a fresh session, spawn a subagent, and ask it to quote the rules back. Anything that reaches it is in the wrong file.

Where the workflow actually sits

One tracked file, and a whole workflow layer that never leaves the machine. The green paths are the four pieces you would carry into another repository.

Decide what is public before you write it

In this setup only CHANGELOG.md is tracked; every CLAUDE.md, all of .claude/, and all of docs/ are gitignored. Whatever you choose, make it a gate rather than a habit: one check that fails the task if git starts tracking something that should have stayed local.

A local layer does not travel

Cloning the repository on a second machine gives you none of it. Copy agents/, scripts/, hooks/, and the settings file by hand. Track the layer instead if your team should share it; the trade is that agent files then live in the repository history.

Know what reaches a subagent

Every CLAUDE.md in the hierarchy does, which is why product rules belong only there. A SessionStart hook's added context does not: it fires for the main session alone. Verify this yourself before you rely on it either way.

Planning moves one direction

An idea becomes a plan, a plan becomes a dispatch brief, and the set moves to archive/ when the feature ships. Keep specs in one folder no matter which tool wrote them, or you will end up with a directory per tool and no single place to look.

Where each layer earns its cost

Three things a gate script cannot catch

Gates are cheap and fast, which is exactly why they are the wrong tool for these. Each pattern below is why one expensive reader stays in the pipeline.

blind suite serialization

The suite is structurally unable to see it

A writer and a reader disagree about a format: local time against UTC, a locale-dependent number, a currency rounded in two places. The bug only exists outside the environment your tests run in, so the suite is green and stays green.

patternEvery test passes. The defect is real and reproducible, just never in the one timezone, locale, or clock your runner uses.
gates miss itA gate can only fail on a condition it actually runs. Adding more assertions in the same environment finds nothing.
review sees itA reader asks which environment the assertion is true in, rather than whether it passed.
fence itRun one suite a second time under the hostile condition, and put that run in the gate script, not only in CI. A fix without a failing-environment test is not a fix.
The rule this produces: when a bug turns out to be invisible to your suite, the deliverable is a new environment for the suite, not just a patch.
false green test quality

The test passes through an unrelated guard

An assertion reads correctly and passes, but for a reason that has nothing to do with the invariant it claims to pin. Delete the behaviour it is supposed to protect and the test still passes.

patternThe test targets a value the component happens to produce anyway, or waits on a condition that was already true before the action ran.
gates miss itGreen is green. A script has no opinion about why an assertion held.
review sees itReading the test against the behaviour it names. Coverage tools will not do this, and neither will a rerun.
fence itSend the finding back to the same agent that wrote the test, context intact. A fresh agent re-derives the whole file and often reproduces the same mistake.
The rule this produces: a green suite is mechanical evidence, not judgment. Budget one reader who is allowed to distrust it.
unfenced risk drift

A risk gets created and only written down

You vendor a component from upstream, fork a config, or patch a generated file. Everything works. The danger arrives months later, when someone re-pulls and quietly discards the local edits.

patternThe task ends with a sentence in a doc: remember that this file has local changes. Nobody reads it at the moment it matters.
gates miss itThere is no gate yet. The risk was created by this very task, so nothing was watching for it.
review sees itA reviewer treats an unfenced risk as an incomplete task rather than a documentation item.
fence itShip the check with the change. Mark every sanctioned edit, record the count, assert it: a task that creates a drift risk also creates its gate.
The rule this produces: if the follow-up depends on a human remembering, it is not done. Convert it into a grep on the same day.

Porting this to your own repo

Four pieces, in the order they pay off. None of them needs anything beyond Claude Code, a shell, and git.

Split the contract file by what it is, not by topic

Rules, decisions, and traps go in CLAUDE.md. Current state goes anywhere else. On one real project this cut a dispatch's reading cost from roughly 230 lines to 82 plus one area file, and the deeper reason is that facts rot while rules do not.

CLAUDE.md          guardrails, conventions, traps
CHANGELOG.md       what shipped
docs/plans/        what is planned
docs/ISSUES.md     what is broken or deferred

Write the agent files by pipeline stage

Divide by stage, not by discipline. Give each file only its role guardrails, pin the models, and give the reviewer no write tools at all.

.claude/agents/
  implementor.md   model: sonnet, tools: all
  reviewer.md      model: opus, tools: Read Grep Glob Bash
  docs-keeper.md   model: sonnet, tools: + Edit Write

Turn your invariants into a script

Anything you would otherwise write as "remember to" becomes a check. One line of output per gate, non-zero exit on any failure, and a test hook so you can prove each gate fails when it should.

$ .claude/scripts/gates.sh --web
$ GATES_DIFF_OVERRIDE="src/x.ts" \
    .claude/scripts/gates.sh   # prove a gate fires

Name your spine, then let grep police it

List the files where one mistake breaks several surfaces at once. Match the diff against that list and refuse to pass until a real review is recorded. This is the one decision that keeps expensive review scarce without leaving the risky code unread.

SPINE='^src/lib/dates\.ts$|^src/lib/queries\.ts$|...'
git diff --name-only | grep -E "$SPINE"
  → instant review required

The model never decides when it is done

Implementors report facts. The script certifies mechanics. One reviewer applies judgment. Acceptance and every commit stay with the person whose name is on the repository.
